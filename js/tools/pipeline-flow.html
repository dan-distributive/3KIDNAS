Fixed: the two dumps used to happen on every call to SingleGalaxyFitter, not once

DumpFittingFixture/DumpBestFitModelCube used to be called unconditionally inside SingleGalaxyFitTests.f's main program — the SAME compiled binary RunWRKP.RunWRKP shells out to for both the one-time initial fit (BSSwitch=0) and every fortran-local per-realization fit (BSSwitch=1, from Bootstrap_Error_Analysis.GetBootstrapModel). BSSwitch=1 only ever happens on the fortran-local leg — UseDCP=1 skips that whole loop in favor of RunBootstrapsDCP — so on a pure fortran-local run with N bootstraps, this binary re-dumped both files N+1 times, into the SAME two CWD filenames, from up to nProcessors concurrent OS processes at once. Nothing on the fortran-local leg ever read them back — pure waste, and the source of the two stray multi-MB files that kept showing up in SingleGalaxyTest/ after a fortran-local run.

Does this explain minor fortran-vs-js/dcp differences? Traced it — no. Each leg's own initial fit (RunWRKP(BSSwitch=0)) is one single, synchronous, blocking call — os.system() doesn't return until PreGalaxyAnalysis → dump → optimizer → dump is fully done. FullSingleGalaxyFit.py's move-to-DCPJobData step runs immediately after that call returns, before the bootstrap loop starts. And UseDCP=1 configs never call RunWRKP with BSSwitch=1 at all (they go through RunBootstrapsDCP instead) — so there was never a window where a per-realization dump could land in CWD before that leg's own move step swept it into DCPjobData. Each leg's fresh initial-fit dump always overwrites whatever a previous leg's process left behind, before it gets moved and consumed. Combined with run_all_three.js running all three legs strictly sequentially (never concurrently) in the same directory, there's no path for js/dcp to ever consume a stale bootstrap-realization fixture. The bug was real waste + an internal race, but it didn't leak across legs — worth ruling out as an explanation for any numerical divergence you're chasing separately.

FFTW: what's actually live, confirmed by grepping the whole repo

FFTW3JS (the hand-rolled engine) is retired from the live convolution path. CubeKernelConvolution.js's own header says so directly: it imports from FFTW3WasmRank2.js, "not FFTW3JS's hand-ported engine (retired from this file)". bootstrap-realization-launcher.js's require list and its job.requires() DCP-bundling list never pull in src/FFTW3JS/* at all — it's unreachable from the live per-realization path. It's kept only as a secondary comparison inside FFTW3WasmRank2.js's own self-test.

The live engine is fftw3wasm-v3 — the real FFTW 3.3.8 C source (third_party/fftw-3.3.8, the same one Fortran links natively), Emscripten-compiled to wasm. Not a reimplementation of the algorithm.

No "fftw3wasm-v2" exists anywhere in this repo (grepped the whole tree). History per the source comments: the local/unpublished package name is fftw3wasm (still what third_party/fftw-3.3.8/wasm/README.md calls it); publishing that name to DCP hit a conflict, so it was republished directly as fftw3wasm-v3 — there was never a "v2" checked in.

Correctness: FFTW3WasmRank2.js's self-test checks its output bit-exact against ground_truth_harness — a real C binary linked against this project's own compiled libfftw3.a. FFTW3JS is only a secondary check in that same test (~1e-14 relative agreement, not bit-exact) — it was never the ground truth, and it isn't in the dependency path that could fail on a different galaxy.

Performance: CubeKernelConvolution.js imports rdft2R2cSyncNative/rdft2C2rSyncNative — FFTW's own native 2D r2c/c2r planner, one fftw_execute call per transform — not the composed row-then-column 1D decomposition (~150–170 individual FFTW calls per channel) that FFTW3WasmRank2.js also exposes but the live code doesn't use. The live path is already the faster of the two available options, on top of being the one backed by real compiled FFTW3.

Net: the "might fail with a different galaxy" risk of the hand-rolled engine doesn't apply to what's actually running today — it's out of the live dependency path, kept only as an internal cross-check.

Why some js-dcp realizations don't converge when fortran-local's don't struggle at all

Most of the apparent divergence isn't a fit problem at all. Traced against a real 1000-bootstrap run (seed=42): 110 js-dcp realizations initially looked like outliers by raw wall-clock time, but only ~9-10 actually have an abnormal evalCount (~5000-5250, vs a typical ~400-450). The other ~101 have a completely normal evalCount — they just landed on a slower or contended real DCP worker machine. That's inherent variance in a heterogeneous distributed system, not a sign anything is wrong with those results (see run_all_three_results.html's Performance table, which now keys its outlier test off evalCount for exactly this reason, not raw totalMs).

The optimizer has a hard cap, shared by both implementations: ITMAX = 5000 (GalaxyFit.js's amoeba; DownhillSimplex.f's own parameter(ITMAX=5000)). A realization that hits it returns noConvergence = true rather than iterating forever — the ~9-10 genuine js-dcp non-convergences above all clustered right at this cap (evalCount 5165-5247, i.e. ITMAX plus per-iteration overshoot).

Of those genuine non-convergences, two different things are going on. Replaying the exact same resample locally (bootstrapSeed=42 + realizationIndex is fully deterministic — the real payload file reproduces it exactly): 4 of the 9 indices (142, 321, 893, 963) ALSO show massively elevated fitMs in fortran-local for the identical resample (up to ~99×MAD from fortran's own median) — these are intrinsically hard bootstrap draws, and both implementations independently struggle on them. But 3 (259, 662, 914) are completely normal in fortran-local (~0×MAD, typical fit time) while js-dcp needed 5000+ evaluations on the exact same data.

Root cause for the JS-only cases, empirically confirmed: cloud particle density. cloudBaseSurfDens (Inputs/SingleGalaxyTestFittingOptions_Base.txt, currently 400) sets particle count per ring (SingleRingGeneration .ring_CalcNumParticles) — both fortran and js read the identical value from the same shared file, so it's not a leg-to-leg mismatch. Replaying realizations 662, 914, 142, 178, and 400 with cloudBaseSurfDens raised to 500 (same seed, same resample, nothing else changed): all 5 went from hitting ITMAX with no convergence to converging cleanly, ~3.7-4× faster. 5 for 5. Consistent with the model's flux discretization being coarse enough at 400 particles/ring that the chi² surface carries enough Monte-Carlo noise for the simplex to never cleanly satisfy its tolerance on certain resamples.

Still open: exactly why js-dcp is the one sensitive to this at density=400 when fortran-local isn't, given both now run the same corrected algorithm at the same density on the same data. Leading candidates, not yet confirmed: JS's per-operation Math.fround float32 emulation accumulating rounding differently than native REAL*4 across thousands of particle-flux summations, enough to occasionally send the simplex down a measurably harder path on a sensitive resample; or a difference in the particle *placement* algorithm itself (not just count) between SingleRingGeneration.js and its Fortran counterpart at equal density. run_all_three.js --cloudDensity <value> (added this session) makes testing either the mitigation or further isolation a one-flag change.
